## Safety là thuộc tính hệ thống

Model, prompt, retrieved data, tools, identity, UI, logging và policy cùng tạo ra behavior. Input của safety analysis là asset, actor, trust boundaries và capabilities; output là risk scenarios, preventive/detective controls và residual risk decision.

State cần theo dõi: `request -> classified intent -> authorized capability -> proposed action -> validated action -> outcome`.

</MdxPage>

## Threat model contract

Một scenario có dạng `(actor, entry point, untrusted data, target asset, attempted capability, impact)`. Ví dụ: document bên ngoài chứa indirect injection; agent đọc document; target là email nội bộ; attempted capability là gửi dữ liệu ra domain ngoài.

Threat model phải nêu assumption và owner. “Prompt injection” không đủ nếu chưa biết tool nào có quyền và hậu quả là gì.

</MdxPage>

## Worked control trace

Agent chỉ cần đọc trạng thái đơn hàng:

1. Browser gửi order ID cùng authenticated session, không gửi provider key.
2. Backend suy ra actor từ session đã xác minh rồi kiểm tra ownership; không tin `actor_id` do client tự khai.
3. Model được cấp tool read-only với schema hẹp.
4. Backend kiểm tra authorization lại khi tool call tới.
5. Log chỉ case ID, decision, latency; PII được redacted.

Nếu model đề xuất refund, backend trả `forbidden`; prompt không thể nâng quyền.

## Pitfall và handoff

- Dùng least privilege, allowlist, confirmation và timeout/cancel.
- Đo unsafe compliance cùng overrefusal theo slice.
- Với toxicity/bias, dùng matched pairs chỉ đổi một group attribute, rồi báo unsafe/overrefusal rate theo subgroup; không suy kết luận từ aggregate đơn lẻ.
- Không đưa secret vào model input hoặc raw log.
- Replay safety eval sau thay đổi model, prompt, data, tool hay policy.

Quiz kế tiếp kiểm tra threat/control contract; refusal calculation đo hai phía của calibration.

## Task-Incremental Learning (TIL)

Trong **Task-Incremental Learning**, việc cần làm thay đổi và hệ thống phải báo cho mô hình task hiện tại.

Một task không nhất thiết phải đổi hẳn từ phân loại sang dịch thuật. Nó cũng có thể là một bài toán con trong cùng hệ thống, miễn là tín hiệu task cho biết mô hình phải dùng bộ đầu ra hoặc bộ phân loại nào. Lab tiếp theo dùng cách này: báo thức, âm lượng và calendar là ba task, mỗi task có hai ý định riêng.

`task_id` không nhất thiết là một con số.

**Yêu cầu 1 — phân loại cảm xúc:**

```json
{
  "text": "The service was slow.",
  "task_id": "sentiment"
}
```

```output
negative
```

**Yêu cầu 2 — dịch sang tiếng Việt:**

```json
{
  "text": "The service was slow.",
  "task_id": "translate_vi"
}
```

Model trả về:

```output
Dịch vụ chậm.
```

Hai request có `text` giống hệt nhau, nhưng router đọc `task_id` để chọn head, adapter, expert hoặc hành vi phù hợp. 

Trong thực tế, ngoài output dưới dạng `API/metadata` như trên, task signal còn có thể xuất hiện dưới dạng:

- **Control token:** input bắt đầu bằng token như `[TASK_TRANSLATE_VI]`.
- **Instruction:** `Hãy dịch sang tiếng Việt` đóng vai trò task signal bằng ngôn ngữ tự nhiên.

<LessonNote>

Điểm cốt lõi của TIL không phải định dạng ID, mà là **model được cung cấp tín hiệu đủ rõ để chọn task khi inference**. Nếu tín hiệu mơ hồ hoặc sai, router có thể chọn nhầm head, adapter hoặc expert; khi đó output vẫn sai dù từng module chuyên biệt đã học tốt task của nó.

</LessonNote>

## Domain-Incremental Learning (DIL)

Trong **Domain-Incremental Learning**, model vẫn làm cùng một task với cùng bộ nhãn; chỉ nguồn dữ liệu thay đổi. Ví dụ, task luôn là phân loại cảm xúc `positive/negative`, nhưng dữ liệu chuyển từ review phim sang review nhà hàng.

Ở domain phim, từ `slow` thường mô tả nhịp phim và có thể là tín hiệu tiêu cực:

```json
{
  "text": "The pacing was slow.",
  "domain": "movie",
  "label": "negative",
  "predicted": "negative"
}
```

Sang domain nhà hàng, cùng từ `slow` xuất hiện trong một ngữ cảnh hoàn toàn khác và có thể khiến model phân loại sai:

```json
{
  "text": "The slow-cooked beef was ok.",
  "domain": "restaurant",
  "label": "positive",
  "predicted": "negative"
}
```

Các domain có thể khác nhau về từ vựng, cách viết và quan hệ giữa từ với nhãn. Tuy vậy, khi inference, API vẫn chỉ gửi text:

```json
{
  "text": "The slow-cooked beef was ok."
}
```

<LessonNote>

Trong nhiều trường hợp, model sẽ **không nhận domain ID khi inference**. Vì vậy, cùng một bộ tham số và sentiment head phải học tín hiệu của domain mới mà vẫn xử lý đúng domain cũ. Đây là phần khiến DIL khó hơn một bài toán chỉ có một domain cố định.

</LessonNote>

## Class-Incremental Learning (CIL)

Trong **Class-Incremental Learning**, task vẫn là phân loại, nhưng hệ thống bổ sung class mới theo thời gian. Ví dụ, bộ phân loại ý định của người dùng ban đầu nhận diện `billing` và `shipping`; stage mới bổ sung `refund`. Ở đây, **intent** là điều người dùng muốn hệ thống thực hiện, chẳng hạn hỏi về hóa đơn, kiểm tra giao hàng hoặc yêu cầu hoàn tiền.

Một record huấn luyện cho class mới có thể chỉ cần:

```json
{
  "text": "I want my money back.",
  "label": "refund"
}
```

Output space của cùng classifier được mở rộng:

```text
[billing, shipping] → [billing, shipping, refund]
```

Khi inference, model chỉ nhận câu và phải chọn trong toàn bộ class cũ lẫn mới:

```output
refund
```

<LessonNote>

  Trong taxonomy của survey, CIL là setting model học thêm class mới theo từng giai đoạn <Cite paper="shi2024continualSurvey" evidence="til-dil-cil-settings-03-shi2024continualSurvey" />. Trong ví dụ của bài, model không dùng task ID để chọn head riêng mà phải phân biệt **tất cả class trong một output space chung**.

</LessonNote>
